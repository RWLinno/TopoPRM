## 5. Result conventions (for server_A merge)

After every aggregation pass `results/baseline/` contains:

- `leaderboard_baseline.csv` ? one row per `(label, benchmark)`, columns:
  `label, benchmark, pass@1, pass@5, maj@5, prm@5, F1, correct, error,
   avg_tokens, elapsed_sec, mtime_iso`.
- `metrics_full_baseline.json` ? the full per-benchmark metrics body, nested
  by label.
- `eval_trace_baseline.md` ? chronological record of every metrics file
  detected, with timestamp / duration / pass@1.
- `missing_cells_report.md` ? `(label, benchmark)` cells still missing,
  including labels that have been launched but haven't produced metrics yet.
- `merge_manifest.md` ? describes the join contract with server_A's
  `results/method_v2/*` (same schema; concatenable via `csv.DictReader`).

Strip the `_B` suffix when copying numbers into the paper's main table; keep
the suffix in the audit trail to track origin.

## 6. Run management notes

- Failure handling: `unified_eval_orchestrator.py` already retries each
  bench once with reduced batch on transient CUDA/OOM. `todo_baseline.sh`
  catches orchestrator-level non-zero exits and continues to the next label.
- Resumability: any `(label, benchmark)` pair whose `_metrics.json` already
  exists is skipped on the next run; pass `--force` to override.
- GPU contention: workloads running on GPUs 1-4 (other users) are not
  touched. `GPU_POOL` defaults to 0,1,2,3,4,5,6,7 but actual launches use
  only the four currently-free cards (0,5,6,7).
- Monitoring: `tail -F results/baseline/logs_B/<label>_<bench>.log` to watch
  per-benchmark progress; `cat results/baseline/logs_B/status_<label>.json`
  for orchestrator-level state.
